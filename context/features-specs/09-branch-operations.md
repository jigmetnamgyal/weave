We're giving the control plane the ability to create a branch in a
granted repository (Unit M3.3), which is the last thing M3 needs and the
first external side effect Weave performs on a customer's repository.

Everything so far has read. An installation was recorded, repositories
were listed, permissions were checked — all of it observation. This
writes: a ref that appears in someone's repository, under our App's
name, attributable to a person. That is a different kind of mistake to
make, and the unit is shaped around it.

## Scope, corrected against the milestone

I described this unit twice as "cloning, branches, commits and pull
requests". That was wrong, and worth stating plainly because the
correction narrows it considerably:

- **Cloning** happens in the **runner** — `context/architecture.md`
  describes it as "a per-session ephemeral environment containing a
  repository checkout". That is M5.
- **Commits and pull requests** are M8, "commit/pull-request delivery",
  and are generated by session-completion activities that do not exist
  yet.
- **Webhook ingestion** was delivered in M3.1 for installation events.

What is left in M3's line is **branch operations**. That is this unit,
and it completes M3.

### Push and pull-request webhooks stay unsubscribed

M3.1 deferred them because nothing handled them. That is still true —
sessions arrive in M5 — and subscribing now would mean receiving traffic
with no consumer, which is the same argument, not a new one.

There is also a second reason, and it must be settled before anyone
revisits this: **the development webhook URL is a public smee.io
channel**, readable by anyone holding the URL. Push payloads carry commit
messages, author email addresses and file paths. Moving off smee is a
prerequisite for subscribing, not a tidy-up afterwards.

## Decisions this unit locks in

- **A branch is created only through `RepositoryForUse`.** It reconciles
  with GitHub before answering, so a grant withdrawn since the page
  loaded is caught. A stored `granted` flag is a belief, and acting on a
  stale one is how a revoked grant reaches a write.
- **Protected branches are never written to.** Invariant 11 says agents
  never write to them directly; this is the first code that could, so it
  is the first place the invariant becomes real rather than aspirational.
  Creating a branch *from* a protected base is fine and normal —
  creating one *at* a protected ref is refused.
- **Creation is idempotent by name.** Invariant 5 requires every external
  side effect to be idempotent. GitHub refuses a duplicate ref with 422;
  that refusal must be translated into "this branch already exists and
  points where you asked", not surfaced as a failure — otherwise a
  retried request looks broken while having done exactly the right thing.
- **Every creation is audited**, attributable to the member who caused
  it, with the repository, base and resulting SHA.

## Naming and collisions

Branch names come from the product, not from the caller. Accepting an
arbitrary string invites `refs/heads/../../` games and names that collide
with real branches.

- Generate the name from a prefix plus a short random suffix, and
  validate it against Git's own rules before sending it. Reject anything
  with `..`, a leading or trailing `/`, control characters, or a `refs/`
  prefix.
- On the 422 that means "already exists", read the existing ref. If it
  points at the requested base, return it as success. If it points
  somewhere else, that is a real conflict and is refused — silently
  handing back a branch pointing at unknown work is worse than an error.

## The operation

- Resolve the base: the repository's default branch unless one is named,
  and the base must exist.
- Create `refs/heads/<name>` at the base's current SHA, using an
  installation token minted for that installation.
- Return the branch name and SHA.

`contents: write` is the permission this needs, and the installation may
not hold it — an App's permission set can be widened after an
installation accepted the old one. Check before attempting, and say which
permission is missing rather than relaying GitHub's 403.

## Authorization

Unchanged in shape, with the third axis from M3.1 doing real work now:

- Membership decides **visibility** — a non-member gets 404.
- Permission decides the **operation** — `repository:manage` is required
  to create a branch.
- GitHub's grant decides **reach** — a repository the installation no
  longer grants is unavailable regardless of role, and this is checked
  against GitHub rather than against our records.

## Tests

- A branch is created, and creating it again with the same name and base
  returns the same branch rather than failing.
- Creating it again at a *different* base is refused.
- A protected ref is refused as a creation target.
- A repository the installation no longer grants is refused, proven with
  the grant withdrawn at GitHub rather than only in our table.
- An installation lacking `contents: write` is refused with the
  permission named.
- Names with `..`, `refs/`, control characters, or leading and trailing
  slashes are rejected before any request is made.
- A member without `repository:manage` gets 403; a non-member gets 404.
- GitHub is faked at the HTTP boundary, as in M3.1 — the 422 handling and
  the token minting are most of what is worth testing here, and an
  interface mock skips both.

## Carried forward, and worth re-reading before starting

**From M3.1, on anything that deduplicates, retries or leases:** the
delivery path took three attempts, and each fix traded one failure mode
for another — deduplicating before the effect dropped failed retries;
recording completion separately allowed concurrent double-execution; a
lease prevented that but acknowledged work still in flight, which GitHub
then never retried. Write down what must happen for each outcome before
choosing the mechanism.

**From M3.2, on the gates:** `make ci` is not a superset of what CI runs
— the API job verifies `go mod tidy` changes nothing and the local target
does not. Decide in this unit whether to add the check or stop calling
the target "every local quality gate"; the present arrangement invites
the mistake it already caused.

**From M3.0, on new tables:** if this unit adds any, `ENABLE`/`FORCE ROW
LEVEL SECURITY` and policies belong in the same migration that creates
them. RLS is off by default, so a table added without them is silently
unprotected and looks entirely correct.

### Check when done

- An owner creates a branch in a connected repository and sees it on
  GitHub.
- Repeating the request returns the same branch without error.
- A viewer cannot create one, and the API refuses them.
- Withdrawing the repository on GitHub makes the next attempt fail,
  without any webhook having been delivered.
- No token or key appears in a log line, verified by grep.
- The `make ci` question above is answered either way, and the answer is
  recorded in the tracker.
- `make ci` and `make test-integration` pass
