## Open Questions

Resolve these before the milestone that depends on them:

- ~~**`make ci` is not a superset of what CI runs**~~ — **Resolved 2026-09-14 in M3.3: the tidy check was added to `make ci`.** The alternative was to stop calling the target "every local quality gate", which would have been honest labelling of a gate that still let a known CI failure through. A local gate exists to catch things before CI does, so the fix was to close the gap rather than document it. `tidy-check` runs `go mod tidy` and fails on a diff, the same shape as `sqlc-check` and `contracts-check`.

- **The generated OpenAPI client does not exist.** `context/code-standards.md` requires one — "use the generated API client; do not call control-plane endpoints through scattered ad hoc `fetch` helpers" — and `apps/web/lib/api.ts` has hand-written helpers and response types for the whole `/v1` surface. The contract itself is now complete and current; what is missing is generation. Closing it means choosing a generator, wiring a drift check into CI so the client cannot silently diverge, and migrating every call site from M2.1 onward. Raised on PR #6 and deliberately not done there: it predates the GitHub endpoints and is wider than any one feature. **Being closed now as Unit M3.2** — see `context/features-specs/08-generated-api-client.md`.

- **Two standards in `context/code-standards.md` are unmet project-wide, raised on PR #10 and verified as real rather than paraphrased.**

  **Cursor pagination** (line 98: "Use cursor pagination for unbounded collections"). The contract has **11 list operations and none is paginated**; 14 list queries carry `ORDER BY` and one carries `LIMIT`. Sessions and transition histories grow fastest, so M4.2 makes it more visible, but it did not introduce it — workspaces, members, invitations, repositories, tasks and agents are all unbounded too. Fixing it properly is one change across the contract, the generated client and every list endpoint, which is why it is not folded into a session unit. **Gate: before the first workspace with real volume, and before M6's session room, which reads histories continuously.**

  **Idempotency keys** (line 100: "Mutations that may be retried require an idempotency key and a documented idempotency scope"). Nothing in the project has one, and `idempotency_keys` is in the architecture's table list but unbuilt. `POST /sessions` is the sharpest case: a lost response today duplicates a row and an outbox record, which is recoverable — but once M5's publisher exists, the same retry starts **two workflows and cuts two branches**, and invariant 5 says every external side effect is idempotent. **Gate: idempotency lands before M5's outbox publisher, because that is the commit that turns a duplicate row into a duplicate branch.**

- **`weave_app` can delete a workspace, and that cascade reaches append-only history.** Raised while fixing a narrower version of it on PR #10. DELETE on `sessions` was withheld there, because deleting a session cascades to `session_state_transitions` and the append-only trigger permits that cascade by design — so the grant was a route to erasing history with nothing raising an error. The same path still exists one level up: migration 00004 grants `weave_app` DELETE on `workspaces`, which cascades to sessions and then to transitions. Nothing in the application deletes a workspace — there is no query, repository method or route — so the grant appears to be unused. Revoking it touches another unit's migration and the tests that cover it, and needs a decision about how a tenant is deleted when that is eventually offered. **Gate: before the first external customer**, alongside anything else that can erase an audit or history trail.

- **List envelope keys are inconsistent across the API.** Six list operations return `{ items: [...] }` and five return a named key — `repositories`, `installations`, `sessions`, `transitions`, `participants` — which is the eleven list operations accounted for. It has been that way since M3.1 and was found in M4.3, when one client consumed all of them for the first time and failed to compile. Nothing is broken; a reader of the contract cannot predict the shape, and every new list endpoint has to guess which convention to follow. Aligning them touches ten operations, their handlers, their tests and the generated client. **Gate: whenever the pagination work happens**, since that rewrites every list envelope anyway and doing both at once costs almost nothing extra.

- **M3.0's browser verification was never closed.** Its Verification Record row ends "Gap: the signed-in browser flow remains unverified", and the 2026-09-11 walk that closed the equivalent gaps for M2.2, M2.3 and M3.1 does not name it. Row-level security is exercised by every signed-in request, so it was almost certainly covered in practice — but nothing recorded that, and an unrecorded verification is an unverified one. Found on PR #13 while a reviewer was checking a different claim. **Gate: fold it into the outstanding M4.3 walk**, which is a signed-in session anyway, rather than making a separate occasion of it. **Closed 2026-09-30** by that walk, operator-reported (Verification Record).

- **The API and the worker share one database role, so a compromised API can reach the cross-workspace outbox claim.** Raised on PR #16 and worth keeping rather than acting on immediately: the reviewer's own conclusion was that the grant matches this project's documented contract — the publisher operation runs as `weave_app`, which is what the spec says — so this is a post-compromise least-privilege concern, not a reachable authorization bypass. No API path calls `weave_claim_outbox_batch`, and `TestNoHandlerActsAsTheSystem` guards the neighbouring shortcut. A dedicated `weave_worker` role with execute on that function and nothing else would close it. **Gate: production hardening in M9**, alongside the other role and deployment-boundary decisions, or earlier if the deployment requires the API and worker to be isolated from each other.

- **A session's own branch becomes a conflict if the base moves between the cut and its completion.** Found building M5.2, raised again on PR #17, and **narrowed there**. `CreateBranch` is idempotent by *name and base commit*. The first shape re-ran the cut whenever *recording* failed, so a database hiccup plus a push to the base was enough to fail a session over a branch it had made itself. Since the review round, cutting and recording are separate activities and the cut's result is durable in workflow history, so a failed record never re-asks GitHub. What remains is the cut activity's own completion being lost — the worker dying between GitHub's response and Temporal hearing of it — followed by a push to the base before the retry. Safe when it happens: the session fails loudly and nothing is overwritten. The fix is to pin the base commit on the session **before** the external write and cut at that commit. **Gate: M5.4**, which checks out that commit and is the first unit to depend on the base being exactly what was cut from.

- **Cancelling a session does not yet remove its branch, and can race the cut.** Raised on PR #17. `CutBranch` checks the session is `provisioning` before calling GitHub; a cancel landing during the GitHub calls cannot stop a ref that is already being made, and `RecordBranch` records the SHA regardless of state — deliberately, because a ref that exists is a fact, and refusing to record it would leave a branch nobody knows about. **Not reachable today:** no API route calls `SessionService.Transition`, and the `transitions` route is read-only, so nothing can cancel a session. The complete answer is not a tighter check before the write — no check can be atomic with GitHub — but cleanup after it: the cancellation path must delete the session branch when `branch_sha` is recorded and the branch has not moved from it. **Gate: the unit that first routes cancellation**, which must own that cleanup.

- **Integration tests and a running `make dev` worker claim each other's outbox rows.** Seen on PR #17's review round. The outbox claim is global by design (M5.1), so a dev worker left running while `make test-integration` runs claims the tests' sessions and runs them on its own queue — here against real GitHub with a fake repository, failing the tests as "unreachable". M5.1 fixed the other direction (the tests putting back rows they did not create) but not this one. Workaround: stop or pause `make dev` while running integration tests. A real fix is a test-only outbox topic or workspace filter, or refusing to start the harness when another worker holds the queue. **Gate: before CI runs integration tests beside anything else that drains the outbox.**

- **An uninstalled App reads as "GitHub unreachable" rather than "repository unavailable".** Found building M5.2. The GitHub port translates `ErrNotFound` to `application.ErrRemoteNotFound` for branches but not for `Installation()`, so an installation deleted on GitHub (webhook not yet processed) surfaces as an untranslated error, is retried five times, and fails the session with the unreachable reason. The outcome is right and the wording is wrong. **A sibling, seen live:** an empty repository reports *"the base branch does not exist"*, which is accurate but does not tell a person that the repository has no commits at all — worth distinguishing when these reasons reach the session room. Translating it is a one-line change to a port M3.1 owns, with its own tests, so it is recorded rather than folded in. **Gate: before M6's session room shows these reasons to people.**

- ~~**Runners are bound to their sessions at the ingestor; NATS publish permissions are not yet scoped.**~~ — **Closed in M5.5a.** The broker now refuses a runner publishing any subject but its own session's, reading the stream, or reading another client's replies; every service identity has a tested allow-list; unauthenticated connections are refused (ADR-014). M5.4a's ingestor-side binding stays as the second layer.

- **A Vercel command's `timeout` is capped at five hours.** Found reading the REST reference in M5.4b: the start command's optional `timeout` accepts at most 5 hours, and a session may run eight. The runner is started **without** one, so it is bounded by the sandbox's own timeout (the lease and the plan cap); nothing in the reference says a command without a `timeout` is capped below that, but Hobby's 45-minute cap cannot show it. **Gate: the nine-hour survival run at the staging gate must run the runner as a detached command with no `timeout` and show it alive past five hours.** If it is killed at five, `SessionMaxRunTime` on Vercel must drop below five hours, or the runner must be restarted within a run, which it cannot be today.
- ~~**Is developing Weave on Vercel Hobby within Hobby's terms?**~~ — **Answered by the operator 2026-09-30: Hobby is used only to test during development; Pro is subscribed before staging and production.** Raised in PR #22's review, since Vercel restricts Hobby to personal, non-commercial use. M5.4b's live tests run on Hobby; Pro stays on the staging gate with the nine-hour survival run and the DPA. No code depends on the answer.
- **Fifteen moderate npm advisories remain, all through `@clerk/ui`.** Found 2026-09-30 when a newly published high advisory (`brace-expansion`, CPU denial of service) turned CI's `npm audit --audit-level=high` red on every branch; that one was fixed by updating `brace-expansion` alone, within its ranges. The moderates come from `@clerk/ui`'s Solana wallet adapters and an old `uuid`; `npm audit fix` would also upgrade the Clerk packages (`@clerk/ui` 1.32.3 → 1.37.0), which is an authentication-library change to take on its own, with the sign-in flow re-walked. **Gate: before the first external customer**, or sooner if any is raised to high.
- **The dev runner backend does not enforce egress.** Recorded in M5.4a's spec before implementation, and in ADR-013. A Docker network cannot express a hostname allowlist; the egress proxy that can is M5.4b. Nothing untrusted executes before M6 — `git clone` runs no repository code, and M5.5's fake provider is Weave's own code — and the dev backend is refused outside development regardless. **Gate: Vercel's firewall (M5.4b) before M6**, the first unit that runs a real agent in a customer's repository — and **per-session logging of every registry request by package path** (M5.4c, through Vercel's `forwardURL`), the control ADR-013 now names for the registry download-count side channel a review of PR #19 found. The dev backend itself stays unenforced; it is refused outside development regardless.

- ~~**Events for a terminal session are quarantined, which may prove too strict.**~~ — **Closed in M5.5b, without loosening the refusal.** A runner's last events no longer race the terminal transition: the workflow halts the runner (terminating — its events still accepted), waits until the stream holds nothing for the session, and only then ends the runner and the session. Measured with ingestion deliberately slowed: without the drain 2 of 5 events were stored; ending the runner before draining stored 1; with the order, all 5 and none quarantined. `session_terminal` and `runner_not_bound` stand as they were.

- **Successful sessions wait in `review_ready` until M7.** Since M5.5b a session whose provider finishes moves `running → review_ready` and its workflow ends; its runner is torn down (ADR-013 keeps no source) and nothing reviews it yet. **M7 must** give these sessions a way forward — review, approve, request revision (which re-provisions from `sessions.branch_sha` plus the stored patch, per ADR-013) — and decide what happens to sessions already sitting there when it ships, including ones whose work was the fake's narration. **Gate: M7.**

- **A paused dev worker still absorbs work.** Found in M5.4a's live check. Pausing `make dev`'s worker with SIGSTOP — the workaround the integration-test interference note recommends — leaves its long-polls open, so Temporal still hands it tasks it can never run: one live session spent a 30-second activity timeout on it, and another had its first workflow task taken by the stale binary and correctly finished on the older workflow version. Stopping, not pausing, is what works; the durable fix is the same as for the outbox interference. **Gate: with that open question — before CI runs integration tests beside a live stack.**

## Session Notes

- **M5.5b's recorded decisions.** (1) **The outcome is chosen by the agent version's model** (`deterministic-v1` succeeds, `deterministic-fail-v1` fails) — something every session already has, not a new field or a test-only switch. (2) **When the exit code and the events disagree, the pessimistic one wins**: a `provider.failed` in history fails the session after an exit of 0, and a failure exit fails it with no such event; decided after the drain, so the history read is complete. (3) **A drain that reaches its bound fails the session** (`events_not_drained`) — ending it `review_ready` would vouch for a history that may be incomplete — and a stream whose retention has been shortened below the drain's need is refused on every read, not only at startup. (4) **The order after a provider's run is exit → halt → drain → teardown → complete**, and halt is deliberately short of teardown: terminating keeps the runner's events acceptable while they drain. (5) **Bounds:** eight hours' maximum run and a ten-minute drain, held by tests to sit well inside the stream's 72-hour retention and the credential's twelve-hour life. (6) **Reasons name the provider**, so a fake-run session says "fake provider" wherever its history is read, and only a provider's validated failure *code* reaches a reason, never its message text.
- **M5.5a's recorded decisions.** (1) **Decentralized JWT** (ADR-014): the only NATS model where a per-runner user is issued without touching the server. (2) **Service allow-lists**, in `internal/adapters/natsauth` in one place: the ingestor gets its stream's JetStream API, consumers and acks; the runner manager gets its stream's information, for M5.5b's drain check; the API gets nothing — its probe is a protocol-level round trip — and an empty allow-list is written as an explicit deny-all because the server reads empty as unrestricted; tests get their own broad identity, never a service's. (3) **No active revocation** of runner credentials: teardown destroys the sandbox, the ingestor refuses events from an ended runner, and credentials expire in twelve hours — active revocation would put the operator key on a live signing path to close a window the first two already close for writes. Revisit at M6. (4) **Credential paths default only in development and test**; anywhere else an unset one fails startup. **Operational consequence for the operator:** a local stack started before this unit holds no credentials; `make dev` regenerates them and recreates NATS with authentication on.
- **M5.4a's three recorded decisions, and one narrowing.** (1) **The runner manager is a Temporal worker on its own queue** (`<session queue>-runners`), with no HTTP API: only it holds the backend's credentials, so only it can provision, as the architecture requires, and with no inbound API there is nothing to authenticate. The queue is derived from the session queue so each test's queues pair up and a `make dev` runner manager can never serve a test. (2) **The runner record**: a `runners` table, row-level security in the creating migration, **one live runner per session enforced by a partial unique index**, the id generated by the control plane and never by the runner, the row written *before* the backend is asked and the handle recorded as soon as it answers — so a crash between the two leaves something the reconciler can resolve by runner id, and the reconciler lists the backend *before* the database so it never destroys an environment provisioned between its two reads. (3) **NATS credentials are not issued in M5.4a**, because the runner does not connect to NATS until it has something to emit; scoped credentials are gated on M5.5. **Narrowed before implementation, and recorded in the spec rather than found in review:** as first written the unit spanned five systems; readiness and liveness now come from the backend's own status, and the dev backend does not enforce egress (gated before M6). Also: `LockSessionForUpdate`'s `FOR NO KEY UPDATE` from M5.3 is what lets `RecordBranch`, transitions and the new runner FK checks coexist without the deadlock M5.3 measured.
- **M5.3's five recorded decisions.** (1) **The ingestor is its own deployment unit**, `services/ingestor`, because the architecture names it a scaling role and because it must neither stall workflows on a poison message nor stop ingesting when Temporal is down; its readiness is PostgreSQL and NATS, and it holds no GitHub key, Clerk issuer or Temporal address. (2) **Unknown event types are quarantined, not stored** — the standards are silent on them, and storing one would persist something nothing downstream can render, from an untrusted producer. Unknown *fields* are ignored and, further than the standards require, **not stored**: payloads are re-encoded from the validated type. (3) **Stream limits:** work-queue retention, so the stream holds only what is not yet ingested; 72 hours and 1 GiB with **discard-new**, so a full stream refuses publishing — loudly, at the producer — rather than evicting un-ingested events; 128 KiB per message, above the 64 KiB event limit, so an oversized event reaches the ingestor and is quarantined with a reason instead of vanishing at the server. The one silent-loss path is an ingestor outage longer than 72 hours, which ingestion-lag alerting (M9) exists to prevent. **Revised in review:** the consumer's `MaxDeliver` is unlimited and the delivery ceiling is the ingestor's own (`ExhaustAfter`, 10), because a transport ceiling loses the event whenever the quarantine write fails on the last delivery. An existing stream whose settings differ fails startup rather than being reconfigured. (4) **The quarantine is not tenant-owned and not readable by the application**: many rows never resolved a workspace, so there is no tenant for a policy to scope by, and a policy with a NULL hole in it would be worse than none. `weave_app` holds INSERT only; operators read it as the owner. No payload column exists, so no code path can store one. (5) **The runner-binding gap is handed to M5.4** as a gate — see Open Questions. Schemas are enforced by strict Go decoding checked against every fixture, not a JSON Schema library, so no dependency was added.
- **M5.2's four recorded decisions.** (1) **System actor for branches.** `CreateBranchAsSystem` skips the `repository:manage` check and nothing else — reach, `contents: write`, protection and rulesets are enforced exactly as for a member. Authorization happened when a member with `session:create` created the session; re-checking a role the system does not hold would either always fail or require borrowing the creator's identity. It takes its workspace and repository only from the session row, and `TestNoHandlerActsAsTheSystem` keeps it out of HTTP. (2) **The SHA lives on `sessions`, not on a transition row**, because cutting a branch happens *during* `provisioning` and is not a state change; a transition to carry it would record a move that never happened. It is write-once twice over: the store compares under the row lock, and a trigger refuses any other path. The version is not bumped, so a member's pause or cancel does not conflict with it. (3) **The audit is written in the same transaction as the SHA, not best-effort beside it** — a deliberate improvement on the spec, which proposed keeping the separate event as a fallback. Neither can now exist without the other. The one window left is GitHub making the ref and the process dying before that transaction; the retry then records the branch as `session.branch_found`, which is true, rather than as created, which it cannot prove — M3.3's rule that a false audit is worse than a missing one. (4) **The worker gains Redis and the GitHub App key, and readiness does not change.** Both are per-activity dependencies under a bounded retry, and a session whose branch cannot be cut is failed with a reason; a worker marked unready during a GitHub outage would be restarted for something it cannot fix and would stop draining the outbox. The worker does not take the webhook secret or the slug.

### Fix — workspace creation failed under row-level security (since M3.0)

Reported by the operator: creating a workspace from the app failed. PostgreSQL
logged `new row violates row-level security policy for table "workspaces"` on
`CreateWorkspace`. Cause: `INSERT ... RETURNING *` makes PostgreSQL apply the
workspaces *read* policy to the returned row, and that policy shows a workspace
only to its members — none exist in the statement that creates it. Latent since
M3.0 because every workspace-creation test ran on the owner connection, which
bypasses RLS. Fix: insert without RETURNING, add the owner membership, then read
the row back as its member. New app-role regression test failed before the fix
and passes after; a reproduction against the dev database now succeeds.
`make test-integration`, lint, typecheck, test, build pass. Separate branch
`fix/workspace-create-under-rls`, independent of M5.4d.3a (PR #29).
